## Release-workflow readiness

The tagged `Build Release` runs for v1.3.17 through v1.3.21 all ended with
GitHub conclusion `startup_failure` and created zero jobs, while v1.3.16 had
completed successfully. The workflow files at both boundary tags and the
current candidate pass actionlint 1.7.12. The repository Actions policy was
then inspected and proved the external cause: it allowed only selected actions,
disabled all verified-publisher actions, and did not allow the exact pinned
SignPath action introduced after v1.3.16. On 2026-09-11 the repository policy
was narrowed to add only
`signpath/github-action-submit-signing-request@c92b958760219087e01f8d67a1669ed57afe2627`;
GitHub's API readback confirmed that exact allow-list entry and retained
`verified_allowed: false`.

This configuration correction permits GitHub to construct the signed workflow
instead of rejecting it before job creation. It does not enable SignPath
credentials or weaken the signed workflow: because the Foundation application
was declined, its named configuration preflight must still fail closed. The
approved no-cost Windows route remains the separate, explicitly labelled
unsigned-beta process in `docs/CODE_SIGNING_POLICY.md`; it must pass installer
identity, SHA-256, NotSigned, Defender, install, and packaged-runtime checks
before publication. A final release tag has not been created during acceptance.
