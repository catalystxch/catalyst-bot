# TEST 7 active-offer heartbeat failure during market evidence compaction

The original TEST 7 profile ran source `6ea1ebba7ff3c271a062416388e3c9bb7b590ecc` from `C:\catalyst\.superpowers\expiry-abort-6ea-build\dist\Catalyst\Catalyst.exe` (SHA-256 `3ED71E414D23FBE5B3B499F253E08EF3F15690CB3B89B16C65121E84D6AFB0F7`, PID 131188). The operator approved and started a new one-day, two-sided MZ campaign `a97ddb10f0ada7c3317f580b07b48c44b9caa8b3b1544385a71935c6d4bc6288`. Coin Prep found reusable coins and sent no transaction. Sage and the native Offers view confirmed three active buys and three active sells. Dexie publication succeeded for the shown offers. Reciprocal Splash peer receipt was not established.

Before a mobile fill, the bot entered terminal read-only `HEARTBEAT_FAILED` at `2026-10-14T11:49:15.648Z`. The bot stopped; the six Sage offers remained active, with zero pending transactions at the subsequent read-only check. The mobile offer was still `active`. The operator was told not to take it while the app is fenced. This run does not satisfy a 24-hour stability or active-offer gate.

The retained original-profile superlog `C:\Users\t_you\AppData\Roaming\Catalyst\bot_superlog_20261014_120756.log` shows bot housekeeping entered `BEGIN IMMEDIATE` at about `11:48:53.958Z` to compact `market_provider_observations`. Its grouped read did not produce the next SQL trace for 12.951 seconds. It then wrote summary rows and issued the expired-row DELETE. The heartbeat attempted four separate `BEGIN IMMEDIATE` renewals from `11:48:55.250Z`, each ending with SQLite error 5 after about five seconds, and failed closed after 20.391 seconds. Housekeeping exited at `11:49:18.953Z` after 27.957 seconds. The log establishes overlapping writer-lock ownership and heartbeat starvation; it does not establish which part of the grouped read, deletion, commit, host I/O, or scheduling caused the long stall.

A later read-only database inspection found 76,665 remaining observations and none older than the incident cutoff. That cannot be used as a pre-failure count: summary rows stamped at `11:48:53.958466Z` prove the incident transaction processed expired observations, including 7,571 from September 14. The initial interpretation that housekeeping had no expired work was incorrect.

The draft mitigation checks for expired observations before acquiring the writer lock and limits a write transaction to 500 expired rows. It summarizes and deletes the same selected IDs, checks the delete count, and leaves later calls to drain a backlog. An independent review found that the initial batch query could still scan the whole table under the writer lock because the existing index began with `asset_id`. A follow-up adds an `observed_at`-leading index. Regression tests first failed against the old implementation, then passed for the no-op lock path, the 501-row two-batch path, an indexed sparse-expiry query plan, and migration of an existing database. An isolated backup of the original database was exercised without wallet access before the index follow-up: the no-expired call returned in 59 ms, then 1,000 rows made expired only in the disposable backup were compacted in two 500-row transactions (125 ms and 318 ms). These measurements do not prove the live 20-second stall cannot recur under load.

The original app remains fenced with the bot stopped. The draft source has not been launched against the original profile. Before resuming the mobile fill test, the patch still needs full-suite, exact-source CI, independent review, package and Defender checks, a fresh original-profile preflight, and the required action-time software-launch and trading confirmations. Harvestr's separate `HEARTBEAT_FAILED` also had four SQLite BUSY retries, but its retained log does not identify this compaction path as the lock holder; no TEST 7-specific repair should be applied there on inference alone.
