## Reproduction and correction

Before the fix, an uncredentialed loopback `GET /` returned the dashboard and set a valid HttpOnly browser session cookie. A second local process could then use that cookie to reach token-protected writes without first receiving a private credential. Red tests reproduced the cookie and write path on the parent `94f12e7c73049d06ac52d201b266255bc59cac05`.

The desktop now supplies an independent per-process browser bootstrap credential on the first navigation. Flask consumes it, binds the browser cookie, and redirects to a clean `/` URL. An uncredentialed or invalid root request returns 401 without a cookie. The Windows `file://` splash passes the credential and sends no referrer; the redirect also sets `Referrer-Policy: no-referrer` and `no-store`. Explicit `SameSite=Lax` is required for Chromium to retain the cookie across the splash-to-loopback top-level redirect; cross-site write requests remain subject to the existing Origin guard. Werkzeug access logging suppresses the bootstrap URL. Browser-only and dev modes print the private first-navigation URL for the operator.

The most sensitive diagnostic GET routes, including status/dashboard logs, crash reports, configuration history/export, and fill export, now require the existing local session or private header token. The tray and internal pricing probe supply that token for their status reads. This change does not claim an exhaustive privacy audit of every read-only API route.
