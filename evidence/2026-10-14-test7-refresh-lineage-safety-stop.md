## Isolated root cause and code path

- On each fresh-wallet cycle, `OfferManager.resume_pending_refresh_lineages` queries every bound, uncommitted refresh parent. Two **older ladder** lineages were returned while the current live book used **Bootstrap** slots. Falling through to ladder-cohort validation classified the current Bootstrap book as a registry conflict and correctly tripped the mutation latch.
- The older buy parent had Task 8 `CANCEL_CONFIRMED` and Task 9 `CANCELLED_PROVEN`. Its replacement child had an exact publication identity, a recorded first-visible time, and later Task 9 `EXPIRED_PROVEN`; the child expired before the parent lineage-commit record was written. The old completion check accepted only a currently visible child, so it could not replay the already proven parent completion.
- The older sell parent and child were terminal. The child was never visibly published; its exact refresh abort was durably `aborted` at 2026-10-14 11:04:01. A completed abort was still included by the pending-lineage query.
- Source commit `26e00917cc67e7897046f98fb0b6bf874edbe1bc` permits proof-only completion when a child was previously visible and has an exact terminal journal, while leaving new cancellation eligibility restricted to a currently visible child. It excludes an exact durably completed abort from pending refresh work. The changes neither create an offer nor clear the live latch.
